# Дизайн: мини-язык описания диалоговых окон

Статус: **дизайн утверждён, реализация не начата.**
Документ — результат проектировочной сессии; содержит все принятые решения
и достаточен для реализации без исходного контекста обсуждения.

---

## 1. Назначение и рамки

Декларативное описание диалогов (окна, тексты, меню, кнопки) как альтернатива
написанию Python-классов прототипов.

- **Главный потребитель** — разработчик бота: эргономика описания вёрстки окон.
- **Обязательное свойство формата** — полная сериализуемость: описание диалога
  можно сохранить (БД, файл) и загрузить в рантайме. Сценарии
  «описания-как-данные» и «пользовательский конструктор» — не первая очередь,
  но формат обязан их допускать.
- **Область модели — только компоновка.** Никаких полей действий или навигации:
  поведение остаётся в обычных aiogram-хендлерах с фильтрами (модель библиотеки —
  фильтро-хендлерная, кнопка не несёт кода). Ценность DSL: хендлер сжимается до
  «изменил `dialog.data` → показал окно», вся сборка сообщения/меню — на модели.
  - Nav-сахар (`goto: window`) возможен позже как *опциональное* поле кнопки +
    библиотечный хендлер — осознанно отложен до реального спроса.
  - Действия (j-perm, реестр Python-колбеков) — вне рамок задачи. Зафиксированные
    принципы на будущее: протокол `ActionExecutor` с непрозрачным payload
    (никакой жёсткой зависимости от j-perm; адаптер — contrib/extra), Python-действия
    только через реестр именованных колбеков, инлайн-`exec` запрещён навсегда.

## 2. Архитектура: три слоя

```
Текстовый DSL ──компиляция──►┐
                             ├──► Ядро: JSON-сериализуемая модель ──интерпретация──► прототипы ──► существующий рантайм
Python-билдер ──построение──►┘
```

1. **Ядро** — единственный источник истины: pydantic-модель, сериализуемая в
   JSON-совместимый dict. Всё остальное — надстройки, компилирующиеся в неё.
2. **Python-билдер** — эргономичный API для разработчика (IDE, типы,
   автодополнение); строит объекты ядра.
3. **Текстовый DSL** — собственный синтаксис, заточенный под типовые операции
   над окнами/меню; парсится в ядро.

**Фазировка: фаза 1 — ядро + билдер** (+ эскиз текстового синтаксиса как
проверка выразимости, без реализации); **фаза 2 — текстовый DSL.**
Обоснование: синтаксис дёшево менять до начала использования и дорого после;
семантика сначала обкатывается на ядре/билдере.

## 3. Ядро: технические решения

- **Pydantic v2** (доступен транзитивно через aiogram, новых зависимостей нет),
  discriminated unions по полю `type`.
- Каноническая форма — **JSON-dict**. YAML — опциональный вход (extra-зависимость),
  без собственной семантики: просто способ записать тот же dict.
- Корень модели содержит **`version`** (int) с первого дня — формат будет жить
  в хранилищах годами, миграции без версии невозможны.

### 3.1. Единица описания — диалог целиком

Модель = именованный диалог: набор именованных окон. Ссылки между окнами —
по локальным именам внутри диалога (нет глобального неймспейса окон);
граф ссылок валидируется при загрузке.

```jsonc
{
  "version": 1,
  "name": "settings",
  "windows": {
    "main":   { /* WindowSpec */ },
    "notify": { /* WindowSpec */ }
  }
}
```

### 3.2. Контент окна — открытый union

Тип контента окна — discriminated union по `type`, спроектированный расширяемым
с первого дня (решение о схеме необратимо, полнота реализации — обратима):

- **Первая итерация:** `text`, `photo`, `document`, `media_group`
  (ходовые для диалогов типы, покрывают ~95% случаев).
- Остальные типы из 13 существующих message-прототипов добираются механически
  по мере надобности.

### 3.3. Универсальный принцип: любое поле — литерал или выражение

Любое листовое поле спеки (текст кнопки, url, caption, значения payload, размер
`chunk`, …) принимает либо литерал, либо узел-выражение. Однострочная логика
пишется прямо в поле; сложная — выносится в функцию реестра или провайдер.

## 4. Язык выражений

### 4.1. Форма: JSON-дерево

Каноническая форма выражения — дерево узлов, **в ядре нет парсера строк**.
Строковый синтаксис выражений (`data.page > 0`) — часть текстового DSL фазы 2
и билдера, компилируется в дерево. Скобки/приоритеты — забота текстового
синтаксиса; в дереве структура задаёт всё сама.

Примерная запись (финальная форма узлов — на усмотрение реализации, важна семантика):

```jsonc
{ ">": [ { "path": "data.page" }, 0 ] }
{ "or": [ { "path": "data.name" }, "аноним" ] }
{ "call": "len", "args": [ { "path": "data.players" } ] }
```

### 4.2. Операторы

`< > <= >= == !=`, `+ - * / %`, `and or not`, `in / not in`,
литералы: числа, строки, `true/false/null`.

- **Семантика `and`/`or` — питонья**: короткое замыкание, возвращают операнд
  (полезно для дефолтов: `data.name or "аноним"`).
- **Ошибки вычисления:** несуществующий путь → `null` (нормальная ситуация для
  опциональных данных); ошибки типов, деление на ноль → исключение
  (баг скрипта, молчаливый null его прятал бы).

### 4.3. Неймспейсы данных — явные

- `data.*` — персистентный `dialog.data`;
- `ctx.*` — разовый context вызова рендера;
- локальные скоупы конструкций: `item`, `index` внутри `foreach`;
- (возможно) встроенные `user.*` / `chat.*` из телеграм-события.

Слитого скоупа нет — коллизии имён исключены, валидатор может проверять ссылки.

### 4.4. Функции: реестр + стартовый набор

`len, str, int, float, bool, round, abs, min, max, sum, join, split, upper,
lower, strip, format, default(x, d), range, sorted, keys, values`.

Реестр открыт: пользователь регистрирует свои **чистые** функции
(тот же принцип, что реестр провайдеров).

## 5. Структурные конструкции (первая версия)

Единообразно применимы к кнопкам, рядам, меню, фрагментам текста:

| Конструкция | Семантика |
|---|---|
| `foreach` | размножить узел по списку: `over` (выражение → список), локальный скоуп `item`/`index`; для кнопок — параметризация payload элементом |
| `if` / `else` | условное включение узла (кнопка, ряд, блок текста, целое меню) |
| `chunk` | раскладка плоского списка кнопок в ряды по N |
| `slice` | узел выражений (start/stop — выражения); вместе с `foreach` покрывает пагинацию |
| `def` / `ref` | именованные переиспользуемые фрагменты внутри модели (кнопка «Назад», общий футер) |
| `provider` | люк: узел вычисляется именованным Python-провайдером из реестра |
| `t` | переводимая строка (см. § 7) |

Сознательно **не** в ядре: виджет-пагинатор, `switch/case`, счётные циклы
(выражаются `foreach` по `range`). **Виджет** = макрос-паттерн уровня билдера,
разворачивающийся в примитивы ядра (например `paginator(...)` генерирует
`slice` + `foreach` + ряд prev/next с if-ами); в сериализованной форме модель
всегда «распакована», интерпретатор о виджетах не знает.

**Целевая выразительность:** люк `provider` нужен только за внешними данными
(БД, сеть) и в редкой экзотике; вся типовая вёрстка выражается декларативно.

## 6. Расширяемость: открытый реестр видов узлов

Пользователь может зарегистрировать собственный вид узла
(`{"type": "my_node", ...}` + класс: валидация + `evaluate()`). Валидация
union'а — динамическая, резолв класса по реестру в кастомном валидаторе.

**Оговорка (важно):** весь стандартный набор узлов — включая `t` — реализован
тем же публичным механизмом (dogfooding), но **поставляется с библиотекой**.
Причины включения `t` в поставку: канон для инструментов (синтаксис перевода в
текстовом DSL, экстрактор msgid для pybabel, `t()` в билдере), портабельность
моделей, универсальность i18n. Цена кастомных узлов — модель исполнима только
там, где они зарегистрированы (та же цена уже есть у провайдеров).

Итого реестров расширения: прототипы (существующий), функции выражений,
провайдеры, виды узлов.

## 7. Локализация

Узел `t` помечает переводимую строку: `{"t": "welcome_text"}`. При
компиляции/рендере опционально передаётся хук `translator(msgid, locale) -> str`;
локаль — из контекста рендера. Нет translator'а — строка отдаётся как есть.
Библиотека переводов не тащится — только точка подключения; msgid статичны в
модели, что совместимо с gettext-процессом (pybabel + обучаемый экстрактор).

Отклонено: прокачка текстов через `data` (модель вырождается в `{ctx.label}`)
и мультиязычные словари в модели (раздувание, несовместимо с po-процессом).

## 8. Кнопки

- **Payload:** поле `data` кнопки — словарь, значения — выражения (литералы —
  частный случай). Вычисляется при рендере; внутри `foreach`:
  `data: {player_id: item.id}` — каждая кнопка несёт id своего элемента.
  Это основной канал «декларативная клавиатура → хендлер».
- **Виды кнопок:** отдельный `kind`-enum не нужен — существующий `ButtonInstance`
  уже покрывает всё через `InlineButtonAdditionalParameters` /
  `CommonButtonAdditionalParameters` (url, web_app, switch_inline_query,
  copy_text, pay, request_*). Спека зеркалит эти поля; строковые значения могут
  быть выражениями (динамические url, startapp-параметры).

## 9. Интеграция с существующим рантаймом

### 9.1. Интерпретирующие прототипы

Модель компилируется (один раз при загрузке) в дерево универсальных
spec-прототипов — `SpecMessagePrototype` / `SpecMenuPrototype` /
`SpecButtonPrototype`, чьи `get_text_content` / `get_buttons` / `get_state`
вычисляют спеку (шаблоны, конструкции, провайдеры) над `(dialog, context)`.

Следствия:
- весь существующий рантайм (инстансы, сторадж, история, фильтры,
  `send_message`) работает без изменений;
- **смешивание бесплатно**: в одном диалоге часть окон — из спеки, часть —
  Python-классами; DSL «импортирует» Python-прототипы lookup'ом по `type_name`
  в существующих реестрах, и наоборот.

Отклонено: параллельный рантайм-путь (двойная поддержка), кодогенерация
(несовместима с рантайм-загрузкой из данных).

### 9.2. Имена и реестр

- DSL-прототипы регистрируются в **общем** реестре (`_registry` существующих
  базовых классов) под детерминированными именами `{dialog_name}:{window_name}`
  (аналогично для кнопок/меню — стабильная схема имён, выводимая из модели).
- Стабильность обязательна: `type_name` хранится в стордже внутри инстансов,
  рестарт с тем же скриптом должен восстановить те же имена.
- **Replace-семантика повторной регистрации — только для spec-записей**
  (перезагрузка модели, hot-reload, загрузка из БД); Python-классы по-прежнему
  падают на дубликате (там это реальная ошибка).

### 9.3. Хендлеры

- `ButtonFilter` уже принимает строки (классы тоже редуцируются к строкам) —
  строковая форма (`"settings:main:save"`) работает из коробки.
- Дополнительно скомпилированная модель отдаёт **типизированные ручки**:
  `model.windows.main.buttons.save` → объект-ссылка, принимаемый фильтром.
  IDE-автодополнение; опечатка падает при старте, а не в рантайме.

## 10. План реализации

**Фаза 1 (ядро + билдер):**
1. Pydantic-модели ядра: диалог/окно/контент (text, photo, document,
   media_group)/меню/кнопка; `version`.
2. Язык выражений: дерево узлов, вычислитель, реестр функций + стартовый набор,
   неймспейсы, семантика ошибок.
3. Структурные конструкции: `foreach`, `if/else`, `chunk`, `slice`, `def/ref`,
   `provider`, `t` (+ хук translator).
4. Открытый реестр видов узлов; стандартные узлы — через него.
5. Компиляция модели в spec-прототипы; регистрация имён, replace-семантика;
   типизированные ручки.
6. Python-билдер поверх ядра; первые виджеты-макросы (пагинатор).
7. Эскиз текстового синтаксиса (документ, без реализации) — проверка
   выразимости ядра.
8. Тесты: вычислитель выражений, конструкции, компиляция, совместимость с
   фильтрами/сториджем; обкатка — переписать 1–2 реальных диалога.

**Фаза 2 (текстовый DSL):** грамматика (включая строковые выражения,
компилируемые в дерево), парсер, диагностика ошибок, синтаксис `t`/импортов.

**Явно отложено:** nav-сахар `goto`, ActionExecutor/j-perm-адаптер,
экстрактор msgid для pybabel, остальные типы сообщений, YAML-extra.
